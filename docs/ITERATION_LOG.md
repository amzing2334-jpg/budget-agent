## 2026-10-27 · 第二轮：有界源码保留与固定前缀对照

状态：`mask-read` 候选、离线回放工具和 CPU 验收完成，真实模型效果待验证。设计与完整结果见 [READ_MEMORY_VALIDATION.md](READ_MEMORY_VALIDATION.md)，官方来源复核见 [INDUSTRY_REVIEW_2026-10-27.md](INDUSTRY_REVIEW_2026-10-27.md)。本轮没有模型推理、训练、租卡或新增模型费用。

### 需求与问题

复核百度两份 2026-07-21 岗位、Seed 官方招聘和三份工程/论文来源，未观察到足以改变项目主线的新要求，也没有确认新 HC。仍应交付可核验的上下文/成本实验、可信轨迹与代码修复结果；仅新增模块不能证明岗位能力。

上一轮发现 mask 轨迹中的重读发生在旧源码已被隐藏之后，停止重复读取的控制器不能直接解决。于是本轮只改变源码保留方式：保留原 mask 的完整动作、来源和最近两条观察，在额外输入额度内加入当前连续 revision 的去重完整源码行。默认额外上限 1024，包含元数据开销，仍受统一上下文与总 token 预算约束；0 时严格等价 mask。原始事件不变，没有额外模型调用，默认策略和默认关闭的循环控制不变。

### 验收与证据

- CPU：**496 passed，8 skipped**；39 个独立 memory 用例、14 个回放用例和既有策略参数化共同覆盖配置、预算、来源、版本边界与无未来信息。跳过项和 SHA-256 见 [回执](../runs/iteration-20261027-01/cpu-validation.json)。
- 对全部 7 条 v5 记录筛选后，纳入 3 条 mask，4 条排除原因完整记录。3 条历史只有同一道任务，共 39 个前缀，0 超限。
- 已知目标行出现共 464 次，mask 可见 4 次，mask-read 可见 226 次；12 个前缀获得更多目标行，仍有 238 次没有保留。
- 每前缀额外输入平均 706.15、最大 1024 个 `cl100k_base` 分析 token。15 个前缀增加输入但没有增加下一步目标读取的可见覆盖，不能只报告覆盖增益。
- [逐前缀回放](../runs/iteration-20261027-01/read-memory-replay/replay.json) 包含原文件哈希、消息/前缀哈希、源码指纹、估算计数器和排除原因；构造只读过去事件，目标动作输出只用于事后诊断。

该回放使用固定 context cap，既不重现新策略下的真实动作，也不推演剩余总预算。它不是成功率、真实重读次数或费用节省实验；cl100k 不是原 Qwen tokenizer。原始真实轨迹仍全部为空补丁，无效旧 GRPO 更新也未变为有效训练证据。

### 下一轮明确的优先级

1. 停止凭同一道旧题继续调记忆额度或堆功能。先准备能产生非空补丁且通过独立测试的真实模型参考配置、环境预检和冻结开发任务清单；具体模型版本与资源仍需核实。
2. 新费用执行前提交具体 GPU/API 方案和费用上限，取得本轮授权。没有新预算时只完成独立的 CPU 检查和方案准备，不复用旧租卡额度。
3. 在相同模型、总预算、任务、资源和采样下，固定 `loop_policy=off`，比较 mask / mask-read / recent，并加入更大近期窗口的简单对照；保存所有失败，报告增加输入后是否更早停止。
4. 若独立评分不能显示收益，保留负结果、撤回默认采用建议；形成有效且合理切分的轨迹后再推进训练闭环。

## 2026-10-26 · 第一轮：可见证据、重复读取与单因素评测

状态：代码与 CPU 验收见 [READ_LOOP_VALIDATION.md](READ_LOOP_VALIDATION.md)；真实模型效果待验证。行业复核见 [INDUSTRY_REVIEW_2026-10-26.md](INDUSTRY_REVIEW_2026-10-26.md)。

### 问题与决定

v5 的真实尝试一直没有有效补丁。旧覆盖诊断显示重复读取，但不能据此把全部重读当成无用：`mask` 会隐藏旧观察，模型可能需要重新获取源码。过去全程加入预算提示也没有获得修复结果。

本轮因此实现范围明确、默认关闭的 `loop_policy=off|recover`。它比较实际送入模型的上下文与刚返回的完整源码，首次发现完全重复时准备一次反馈；反馈确实进入模型调用且后续连续重读时，才以 `stalled` 结束。原始工具输出、补丁与独立评分保留，反馈正常计入预算。不限制必须编辑，不猜测 shell/polling/recall 是否产生新信息。

`paired --factor` 现在可以控制 `strategy`、`decision_policy` 或 `loop_policy`，其余配置、模型、源码和任务必须相同。可信评分判据同时用于配对和报告，避免未评分/矛盾记录冒充胜负。

### 本轮最重要的发现

重新分析历史 7 次尝试，只发现 3 个“实际请求中已经可见的重复读取”事件，每个都出现在不同 `recent` 运行的最后一个工具步骤。3 条 `mask` 运行均为 0；外部 mini-SWE 的 shell 协议不在文件读取判据范围内。这不否认旧覆盖统计，也不证明重读有用；它证明“历史重复覆盖”和“当前可见证据重复”是不同问题。

**本控制器不能被声称已经解决旧 mask 轨迹的停滞，更不能声称提高 SWE-bench 成绩。** 回放没有给旧模型发送新反馈，不能推算提前停止后会节省多少真实 token。脚本化软件场景只验证执行契约。

### 下一轮顺序

1. 优先研究 `mask` 隐藏后恢复源码的具体范围与预算代价，判断保留哪些源码证据能减少反复获取。若做新上下文策略，保持工具、模型、预算和 loop_policy 固定，给出可见证据与恢复成本的直接测量；先与简单保留基线比较，不堆摘要/多 Agent。
2. 准备真实模型参考配置与环境预检。当前 4B/7B 开发诊断没有有效修复；需要先得到有独立评分的参考修复，再扩大开发任务。模型变更的成功不能归因于上下文机制。
3. 模型配置与付费资源到位后，固定任务清单/模型版本/预算/镜像/尝试规则，分别比较上下文策略和 loop_policy，不同时改变多个因素。保存所有失败与空补丁；任务已经用于开发时不得包装为独立最终评测。
4. 形成有效轨迹后再讨论 SFT/偏好/RL；无效旧 GRPO 更新仍不可用。没有独立有效评分和可解释的数据切分，不能进入训练收益叙事。
