## 轨迹揭示的主要瓶颈

三种策略都只读取了 317 行目标模块的前 100 行，随后尝试通过 `write_file` 重写整个文件。768 token 的单次输出上限使较长的 JSON 编辑动作被截断，导致协议解析失败。这个组合使 Agent 在有效完成局部编辑之前就消耗了大量预算。

- `recent` 三次重复“读取前段、尝试长 JSON 编辑、解析失败”的过程，没有任何成功写入，最终没有补丁。
- `structured` 后续成功提交了一个很短的整文件写入，将原来的 317 行模块覆盖为 5 行，并留下未闭合括号。
- `summary` 后续将该模块覆盖为 36 行，删除了必要函数与实现。
- 后两者都执行了提示示例中的 `python -m unittest discover -s tests -v`。该仓库位置的 `tests` 目录不可导入，Agent 收到的是测试发现失败；轨迹中没有完成 `diff` 检查或 `finish`。

后两种策略产生非空补丁不代表进展更好：它们的补丁破坏了源码。现有证据更直接支持“全文件写入与短输出预算不匹配、测试示例不适配真实仓库”这一诊断，而不是支持某种上下文策略获胜。

这仍是单题观察。它没有证明所有失败都能由工具改进解决，也没有排除模型能力、提示遵循和仓库理解不足等因素。下一步应先改变最接近失败的接口，检查预测是否成立，再决定是否扩大上下文实验。
