# 飞书笔记研读：Coding Agent 求职与项目取舍

分析日期：2026-10-22。对象为 Tiez 的[《全网大模型面经答案整理+学习路线笔记+前沿技术（持续更新）》](https://my.feishu.cn/docx/ZKEYdx3yxofr9nxc3kQczl5XnJb)。本文件是针对当前项目和求职阶段的原创分析，不是原文转存，也不是对作者身份或所有技术答案的背书。

**判断：继续做 Coding Agent，但下一阶段应从“功能和审计链路齐全”转向“能真实修复、能解释失败、能证明一个改进有效”。固定预算是有价值的实验设定，本身还不构成技术贡献。**

**需要纠正或加上条件的内容。**

1. 前面将多次采样、挑选正确答案再训练笼统称作 RL，省略了优化目标。筛选成功样本后用交叉熵学习属于拒绝采样后的 SFT；只挑选最好答案而不更新参数是推理策略。GRPO/PPO 要说明奖励、优势、采样策略与参数更新。后文 43 和 47 已补充规则奖励与策略梯度内容，应把前后章节对齐，不能据此说全文不了解 RL。[DeepSeek-R1 原报告](https://arxiv.org/html/2501.12948v1)分别描述 RL 与拒绝采样/SFT。

2. SFT 不是所有 RL 的逻辑前置条件。R1-Zero 在预训练基座上直接进行 RL；R1 使用冷启动数据。这不意味着我们目前弱基础策略应直接跳过 SFT；训练选择要看行为能力和信号质量。同一原报告支持这个区别。

3. 第 9.7 节用是否有 Reward Model 解释 on-policy/off-policy，理由不成立。关键是采样策略与正在优化的策略之间的关系；奖励可以直接来自环境测试，不必训练独立神经奖励模型。第 8.4 节也提到了 Online DPO，不能把 DPO 理解为永远不能在线迭代。[PPO 原论文](https://arxiv.org/abs/1707.06347)、[DPO 原论文](https://arxiv.org/abs/2305.18290)。

4. 第 43 节将 KL 比作“成绩突然太高就不给奖励”，容易误导。KL 衡量策略输出分布偏离参考分布；它不直接判断成绩是否异常，也不自动检测作弊。任务奖励高与 KL 惩罚高可以同时发生。规则测试奖励仍可能有漏洞，需要独立验证，不能把 KL 当成防钻空子方案。

5. “信息进入上下文即可准确获取”过强。可见、检索到、被正确利用是不同条件。我们的 A 组轨迹中错误反馈仍在请求里，模型仍重复失败编辑；B 组完整搜索结果给出了正确路径，仍没有正确读取。这是本项目的直接证据。长上下文研究也记录过位置敏感性，但其具体幅度不能直接外推到所有新模型。[Lost in the Middle](https://arxiv.org/abs/2307.03172)。

6. MCP 是上下文和工具等能力的交换协议，实际执行来自实现工具的服务和应用运行时；function calling 也不能理解为模型自己已经执行了代码。MCP 本身不规定应用如何推理或管理上下文。接入 MCP 可解决互操作问题，不能单独作为修复能力提升证据。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)。

7. BLEU、ROUGE 或语言模型困惑度可以服务特定分析，不能替代仓库修复的可执行测试。DPO 更稳定、PPO 泛化更好等判断也依赖任务、数据、实现和预算，不能作为无条件方法排名。预训练规模、某团队卡数、某年岗位门槛属于带日期的案例，不宜背成现行通则。

以上不是对全文的逐项技术审校；它们是最可能影响我们项目选择和面试表达的关键点。

**对现有项目的诚实判断。**

当前项目已经具备预算审计、原始请求/回复、模型与 tokenizer 版本记录、轨迹、Docker 环境、独立官方评分与正负补丁对照。最近记录的 CPU 检查是 262 项通过、2 个可选训练测试模块跳过。这些证明软件链路的部分性质，不能证明模型能修复代码。

v4 的实际情况是：同一个已反复调试的 Astropy 开发任务，两个模型各两种历史格式，共四次尝试；均为空补丁，成功编辑为零，没有执行 run/diff。官方记录 `resolved=null`、`tests_executed=false`。可以说四次都没有交付修改，不能包装为已完成四个任务的官方评分统计。详情见 [v4 验证记录](VALIDATION_V4.md)和[失败分析](V4_FAILURE_ANALYSIS.md)。

最有价值的失败证据有三项：

- 一次目录输出 71,052 字符；B 组各轨迹的三次大目录后续输入就占用 22,272 token，即 32,000 总预算的 69.6%。这是确定存在的浪费，但尚未证明限制目录后能提高修复率。
- A 组面对编辑文本匹配两处的错误重复原动作；反馈在主要循环中仍可见。B 组收到正确搜索路径后仍添加错误前缀或重复浏览。因此不能统一归因于遗忘。
- 尾部预算只剩 1 或 43 个输出 token，实际生成均被截断；其中 43 个 token 的调用未完成正在生成的编辑 JSON。预算规则允许发起输出空间极小的调用，应单独改进和统计，不能把这些尾部截断当作模型自发的格式退化。

过去 v2 的 GRPO 更新因评分解析错误已失效，不是有效训练证据；后续必须重新采集合法 rollout。当前不宜再通过“又增加一个模块”表达项目进步。

**建议保留的项目定位。**

固定预算下的仓库修复 Agent：工具交互、证据管理与失败恢复。

第一阶段回答：在受限成本下，系统能否完成真实的定位—修改—测试—补丁提交？第二阶段只选一个可证伪问题：在模型、工具和预算固定时，保留可定位且不过期的关键代码/测试证据，能否相对最近历史和简单观察裁剪，减少无进展循环，改善修复结果或达到相近结果所需的成本？

第三阶段再考虑预算分配：什么时候追加搜索、读文件、运行测试，什么时候直接修改或停止？第 48 章提示了自适应决策的思路，但它是后续扩展，不能与第二阶段所有变量一起加入。

这条路线具有向后训练、评测环境和系统性能三个方向延展的空间。技术深度最终来自可检验结果与实现理解，不来自题目中的 Agent、Memory 或 RL 字样。

**实施顺序和验收门槛。**

1. 建立可靠参照。用固定版本的 [mini-SWE-agent](https://mini-swe-agent.com/latest/) 与具备可用代码/工具能力的模型跑一个预先确定的小开发集。API 模型可以作为参照；外部 API 不允许我们直接更新其参数，但不妨碍运行机制和评测研究。参考 harness 与我们的工具不同，应将整系统比较与内部单变量消融分开。

2. 修复已知的工具与预算问题。目录查询支持范围、上限与继续读取信息；编辑失败给出能指导重新定位的反馈；一次动作及路径语义清楚；预算不足以完成动作时正常停止。验证放在外部边界，不添加静默纠错、宽泛异常吞噬或掩盖模型失败的自动兜底。逐项改动，保留原始失败样本。

3. 建立有信息量的轨迹与失败分类。区分协议、定位、修改、验证、基础设施和预算失败；同时识别失败动作重复及“工具成功但没有新证据”的浏览循环。指标是诊断工具，不把成功读取或合法 JSON 当成修复奖励的替代品。

4. 冻结一个上下文机制。先比较 recent、简单 observation masking 和候选证据策略。所有方案共用已经修好的工具；不要让新方案额外获得未计费的摘要模型或更多尝试。记录证据来源、文件版本及测试结果对应的补丁版本。摘要可能失真，版本标记可能误删仍有效信息，这些都需要负面案例与消融。

5. 做独立确认。建议先 5–10 个固定开发任务，随后按预算扩大到约 20–50 个未参与调参的任务。这是项目规模建议，不是统计充分性保证。任务选择、重试数、停止条件提前写明；同一任务各方案配对比较，报告全部结果和不确定性。不能不断查看确认集再继续调策略；公开基准也不能承诺没有预训练污染。

6. 按证据选择学习方法。协议薄弱但已有正确示范，可考虑轨迹 SFT；有同问题的可靠偏好对，可研究偏好优化；有可验证奖励、可解任务与有差异的采样结果，再考虑局部 RL。训练前能重放轨迹，训练后看独立任务结果。不能凭 loss 下降或单题成功声称能力提升。

若参照系统仍全部失败，先排查环境、模型、任务难度和接口兼容，不急着宣布上下文策略无效。若简单 masking 与复杂策略相当或更好，应保留简单方案并解释边界。

**评测口径。**

主结果应同时展示：是否产生补丁、评分是否实际执行、是否修复、基础设施失败、输入/输出/缓存 token、模型调用和工具次数、端到端时间与费用。工具总耗时、prefill/decode 在可以可靠测量时分列；无法取得内部推理时间就明确使用 API 或客户端测量口径，不编造。

固定 token 上限只是一种预算定义，不等同于固定 FLOPs、固定 GPU 时间或固定账单。跨模型参数量、tokenizer 和缓存收费不同，必须另作解释。摘要、重试、并行分支与失败尝试的成本都应计入。先展示质量与成本的关系，避免用一个可调惩罚系数遮蔽二者。不能通过提前失败来获得看似更优的低成本指标。

**如何与 Agentic RL 接起来。**

对一次真实交互，输入应包括 issue、当前代码状态和允许的历史；输出是待执行动作；环境返回真实结果。最终奖励以受保护的独立验证为依据，训练输入不包含 gold patch 或隐藏测试。若训练完整策略，通常只对模型生成部分计算策略/SFT 损失，环境观察不是策略生成的动作，不能一并学成模型应输出的文字。

组内所有候选得到同一任务奖励时，相对优势的任务信号为零。额外格式奖励可能使总奖励不相同，但模型可能只学会格式；KL 等项也可能仍产生更新。因此“程序在更新参数”不代表代码修复能力在学习。应记录奖励的各组成、有效样本组、策略版本以及 rollout 与更新之间的关系。

短期可以选择一个窄问题，例如依据明确编辑失败反馈修正下一步动作，并在未见文件/任务上验证。不能只训练记住某条错误提示的固定答法。是否值得用 RL，应与规则接口改进、简单 SFT 等替代方案比较。

训练与模型推理继续放在云端；当前分析没有启动任何训练或租用。算力需求需要在模型大小、上下文长度、采样组数、并发和更新方式确定后估算，不能承诺一张消费卡足以完成所有 Agentic RL 设定。

**你的学习应与项目同步，优先建立能现场展示的能力。**

| 能力 | 学到什么程度 | 对应本项目中的验证方式 |
|---|---|---|
| Python 与软件工程 | 能独立阅读、修改、调试；理解异常、数据结构、进程和异步 | 30 分钟内给文件查询加范围/分页，或修正预算尾部停止；解释关键回归检查 |
| Transformer 基础 | tokenization、chat template、attention 张量维度、mask、KV cache、prefill/decode | 沿一条实际请求解释为什么历史角色和 token 计数会改变行为 |
| PyTorch 与 SFT | 张量操作、autograd、交叉熵、label mask、LoRA 更新对象 | 在云端完成一个可解释的小实验，检查只训练模型输出部分；不能仅运行现成命令 |
| RL 与偏好优化 | reward/advantage、概率比、clip、KL、on-policy 与采样关系 | 给一组奖励计算相对优势，解释全组相同的情况；说明 SFT/DPO/RL 的不同证据需求 |

| 系统能力 | 资源隔离、超时/取消、状态持久化、队列与吞吐测量 | 用一条远程任务说明请求、执行、返回、失败和恢复；围绕实测瓶颈优化 |

笔记中的“Python/PyTorch 速成、边用边查”可以理解为尽快开始实践，不能理解为编码能力可以跳过。用户目前最需要防止的是：仓库由 AI 快速变大，而自己无法在现场解释和修改关键路径。能独立维护一个小而完整的循环，比拥有大量未掌握模块更有求职价值。

网络协议背景可以迁移到超时、资源调度、RPC、并发与测量；这是可利用的起点，不自动等于具备大模型系统经验。近期以 Coding Agent 系统/评测/数据类岗位为主要适配目标，后训练岗用可靠的训练结果补强。基础模型研究岗应作为更长周期目标，不应把一次小模型 LoRA 或 GRPO 冒充基座研发经历。

**六周主线与两周选修。**

以下假设每周约 20–25 小时，不是保证完成日期。若时间不足，优先缩小样本与扩展范围，保留实验控制和个人掌握程度。

| 时间 | 要完成的工作 | 可交付的证据 |
|---|---|---|
| 第 1 周 | 吃透一条失败轨迹与核心调用链；补 Python/模板/工具基础 | 独立定位首个偏离任务的步骤，完成一个小模块修改 |
| 第 2 周 | 可修复的参考系统；有界工具与动作预算 | 真实定位、修改、测试和补丁链；仍全错则继续诊断，不开始方法排名 |
| 第 3 周 | 固定多仓库开发集与失败分类 | 完整尝试记录、有效行为及成本分解 |
| 第 4 周 | 一个上下文假设及简单基线 | 单变量比较和能推翻自己假设的消融 |
| 第 5 周 | 冻结配置、独立任务确认 | 全部结果、不确定性、质量与成本关系、失败边界 |
| 第 6 周 | 清理代码、复现文档、技术报告与面试练习 | 十分钟完整讲解；现场修改；如实界定个人贡献 |
| 第 7–8 周 | 二选一：轨迹 SFT/局部后训练，或推理与调度性能 | 前者须有有效轨迹和奖励，后者须有真实瓶颈；不同时铺开两条大工程 |

**自测问题。**

1. 为什么这条轨迹只生成 131 个输出 token，却耗完 32,000 总 token？
2. 模型看到 `found 2` 后为什么仍重复编辑？哪些解释有证据，哪些还只是猜测？
3. 为什么“合法工具调用率更高”不等于“修复率提高”？
4. 为什么不直接用 recent 或 masking？你的策略在什么任务上会更差？
5. 摘要删除了失败证据、文件修改后旧测试失效，系统怎么记录与判断？
6. 相同 token 上限为何不是相同计算量？如何处理缓存、工具等待和失败重试？
7. DPO 的 rejected 应如何构造，怎样排除长度或格式捷径？
8. 哪些 token 参与 SFT/RL loss，为什么不训练环境输出？
9. 全组任务奖励相同时会发生什么？格式奖励是否可能掩盖无修复进展？
10. 测试环境失效、空补丁、错误补丁为什么应分开统计？
11. temperature=0 为什么不能保证跨硬件、内核与批处理条件的逐位复现？项目实际固定了哪些条件？
12. 给你一个没调试过的失败案例，你能否提出最小对照，而不是立即增加规划器或换框架？

这份材料应作为查缺补漏和模拟追问的索引。后续项目工作的完成标准是可复核结果、可解释机制和独立动手能力；框架数量、代码规模、测试数量或术语覆盖都不能替代这些证据。
