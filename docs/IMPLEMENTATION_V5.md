# v5：从“功能齐全”推进到“能诊断并完成真实修复”

日期：2026-10-22。依据是[飞书笔记研读](FEISHU_NOTE_CAREER_ANALYSIS_2026-10-22.md)、[v4 真实失败记录](V4_FAILURE_ANALYSIS.md)和本轮代码检查。实现与验证状态分别记载；本文不提前宣称模型效果改善。

## 项目应深挖什么

当前最缺的是一个稳定、可解释的真实仓库修复闭环。v4 的两个模型、两种历史格式，共四条轨迹都没有成功编辑、执行测试或查看 diff，最终为空补丁。这个阶段直接比较高级记忆策略，测到的主要可能是协议遵循和模型能力，而不是上下文方法的效果。

笔记对项目最有用的启发，是把基础知识连接到可以追问的工程决策：为何这样序列化历史，如何执行与恢复动作，怎样构造可信奖励，为什么某个对照能区分不同解释。框架、RL 算法和术语数量不是项目完成度。

| 要深挖的能力 | 当前具体缺口 | 本轮落实 | 下一步证据 |
|---|---|---|---|
| Agent 与环境的交互 | 全仓库目录很长；路径示例被照抄；歧义编辑反复失败 | 有范围和分页的查询、精确路径语义、定位反馈 | 真模型是否减少重复并完成 read → edit → run → diff |
| 预算与推理系统 | 输入重发昂贵，末尾仍可能发起只剩几 token 的调用 | 动作额度下限、共享账本、逐调用诊断 | 所省调用是否减少无效尾部；有无误停本可完成的短动作 |
| 评测与错误归因 | 最终空补丁无法单独说明失败机制 | 协议、输出上限、重复失败、重复成功观察分别记录 | 固定任务上的完整结果与失败原因，不挑成功轨迹 |
| 基线和实验控制 | 自己的 full 不能替代成熟 Agent | 真正 mini-SWE-agent 的固定版本入口 | 同模型在外部 harness 是否可修复，分开呈现协议差异 |
| 后训练的数据基础 | 没有可靠真实成功轨迹；历史 RL 更新无效 | 本轮不扩大训练；保留可核对的执行与评分记录 | 有效示范、可靠奖励、有差异的采样结果后才决定 SFT/RL |

## 已实现的改动

### 1. 查询结果有界，且可以继续查

`environment.py` 中 local 和 Docker 共用同一份文件工具实现。Docker 仍通过隔离容器执行；共用函数消除了两套行为漂移，没有新增插件框架。

| 工具 | 参数 | 默认与边界 |
|---|---|---|
| `list_files` | `path, offset, limit` | `.`、0、100；limit 最多 200；稳定目录遍历顺序 |
| `search` | `query, path, offset, limit` | 范围默认 `.`；每页 50 个匹配行，最多 100；不是按文件计数 |
| `read_file` | `path, start_line, end_line` | 默认 100 行，单次最多 200 行；返回总行数、实际区间和下一起点 |

列表、搜索和读取正文每页最多 16,000 字符，元数据头另计。搜索命中保留路径和行号，长行保留命中附近片段。文件读取的单行最多显示前 1,000 字符，并标明截断。`has_more / next_offset / next_start_line` 使截断成为显式可导航状态。

查询逐目录、逐文件处理，不再为了列目录而把全仓库文件字节读入内存。`read_file` 为计算准确总行数仍扫描完整文件；`revision/patch` 原有全仓库处理尚未优化。分页依赖当时文件状态，不承诺跨修改的一致快照。超长单行没有字符级续读参数，可使用环境中有针对性的 shell 命令。

### 2. 编辑失败可定位，不替模型猜修改

`edit_file` 仍要求 `old` 非空且在当前文件中唯一精确匹配。失败时文件保持不变，返回匹配数量、最多五个行列位置，以及重新读取并扩展唯一锚点的建议。零匹配时只尝试定位 `old` 的第一条非空行，不进行模糊替换。

系统提示移除了 `relative/file.py` 等容易被照抄的路径示例，明确要求从观察复制实际仓库路径。参数类型在模型输出入口校验，范围在工具入口校验；错误作为观察返回，编程错误照常抛出。没有自动“修好”多 JSON 回复、隐藏失败、替模型搜索答案或重试调用。

### 3. 为下一步动作预留可配置额度

新增 `min_action_output_tokens`，默认 128。建立下一次输入时保留这部分额度；真正发起调用前，再检查剩余累计 token、上下文和费用限制。摘要与动作继续共用一个 `Budget`，摘要可能改变余额，因此不能只检查一次。

128 是待检验的工程默认值，不是“足以完成所有动作”的定理。短 `finish` 可能用不到 128，长代码编辑即便有 768 也可能截断。这个参数限制的是**允许发起调用的最低输出额度**，不是强迫模型生成至少 128 个 token。显式设为 1 可以做对照；不够时停止，不偷偷增加总预算。

新增配置：[cloud-v5-qwen7b.toml](../configs/cloud-v5-qwen7b.toml)。与 v4 保存的轨迹相比，工具、提示和预算行为均有改变，不能把新旧差异宣称为上下文策略收益。旧 `result.json` 不回填新默认配置。

### 4. 行为诊断进入结果、CLI 和报告

每次内部运行的 `result.json` 新增 `diagnostics`。HTML/Markdown 增加逐次行为表。旧结果没有这一字段时显示 `unavailable`，报告不偷偷解析旧轨迹或补写原结果。

另提供显式离线回放：

```powershell
.venv\Scripts\python.exe -m budget_agent diagnose --input runs/cloud-v4-20261022-01-protocol --output runs/my-v4-diagnostics.json
```

输出路径必须不存在。命令读取 `trajectory.jsonl/calls.jsonl`，不调用模型、不修改源记录。

指标包括成功读取/编辑/命令/diff，非法动作，达到输出上限的非法动作，同版本相同失败动作重复，同版本相同成功观察重复，逐工具返回量和耗时，以及显式观察在输入中出现的字符量。协议错误和达到输出上限可以同时成立；不能由后者直接断言前者由截断导致。观察关联的请求 token 含整个输入，可能重叠，不能相加当作单个事件的精确成本。

成功执行工具不等于正确修复；重复读取也可能是合理复查。这些指标用于定位问题，不作为隐藏测试奖励的替代品。

### 5. 固定上游外部参考

`scripts/run_mini_swe_baseline.py` 默认只打印计划，`--execute` 才能在 Linux CUDA 主机执行。它直接调用 mini-SWE-agent v2.4.6 固定 commit 的 `DefaultAgent`，沿用官方文本动作解析与提示，适配本项目 HF 精确 token 计量和 Docker 环境。

这条参考有完整历史、Bash 动作和上游显式提交语义，属于不同 harness。与内部 JSON 文件工具不同，不能把两者差异归因于上下文。版本核验、完整命令、独立评分和空提交行为见 [MINI_SWE_BASELINE.md](MINI_SWE_BASELINE.md)。CPU 测试覆盖适配契约，但真实上游加载和模型运行仍需云端确认。

## 下一轮实验先回答一个问题

**固定同一模型和任务，v5 是否能完成实际定位、修改和验证；若失败，成熟参考系统是否也失败？** 先回答这个，再谈上下文改进或训练。

建议云端首轮只做三个预定尝试，使用既有开发题 `astropy__astropy-12907`、相同固定 Qwen2.5-Coder-7B checkpoint、greedy、8192 上下文、32000 总 token、768 单次输出、20 步：

| 尝试 | 工具/历史 | 动作额度下限 | 用途 |
|---|---|---:|---|
| V5-1 | v5 内部工具，chat + recent | 1 | 新工具/提示下的尾部调用对照 |
| V5-128 | 与 V5-1 相同 | 128 | 只检验输出下限影响；不称上下文消融 |
| MINI-128 | 固定上游 textbased、完整历史 | 128 | 外部 harness 能力参考，单独报告 |

三次是有上限的计划，不保证租期内都完成。先验证 Docker 和模型资源；接近租期截止就保留未完成状态并释放实例，不补跑、不自动延长。每次输出独立目录，补丁由独立官方评分器检查。若单题仍均失败，不用更大的多策略表掩盖这个事实。

v4 旧轨迹只作历史失败描述。若要严格估计“工具改动的收益”，须使用保存的 v4 源码包和一致输出下限重跑；不能只比较新旧数字便排除提示和版本差异。当前 `paired.py` 的配置/代码指纹检查不为这类跨版本比较放宽。

首轮若出现可复核的修复，再扩展到**预先固定的 5–10 个多仓库开发任务**。现有 pilot 五题均为 Astropy，不能冒充多仓库验证。随后才值得实现简单 observation masking，并与 recent、单一候选证据策略在同代码和预算下比较。候选假设是“编辑后的文件级证据失效能减少不必要重读且不损害正确性”，它尚未实现或得到支持。

正式确认集应在调参前冻结并与开发集区分，按预算逐步扩大到约 20–50 题。任务数不是统计充分性的保证。报告全部尝试、评分执行情况、空补丁、基础设施失败、token、时间、费用与不确定性，不能仅平均成功样本的成本。相同 token 预算也不等于相同 FLOPs、GPU 时间或实际账单。

## 何时进入后训练

如果瓶颈是协议而已有正确示范，先检验窄范围轨迹 SFT；如果同一任务可得到可靠正负例，才考虑偏好优化；只有环境和奖励可靠、策略能生成有差异的任务结果，才进入局部 RL。需要同时记录策略版本、动作 token mask、奖励各组成、有效样本组和独立任务结果。

本轮未训练。历史 `learning-v2/grpo` 仍是评分错误影响的无效更新，不能复用来证明 RL 效果。仍无真实仓库修复成绩时，添加更多训练框架不会解决项目的首要缺口。

## 你要亲自掌握的三条路径

1. 沿 `runner → context → budget → model → environment → diagnostics` 解释一条请求：输入为何这么长、动作额度为何是这个值、失败如何回到下一步。
2. 手动完成一次“歧义编辑失败 → 阅读候选位置 → 唯一精确编辑 → 运行测试 → 查看补丁”，说明为何公开测试通过还需要独立评分。
3. 给出一个能推翻自己方案的对照：若 masking 相当或更好、额度下限误停短动作、文件级证据仍过期，应如何承认结果并修改方案。

这些能力可以在面试中通过代码、轨迹和现场修改核验。项目应以真实问题与证据建立深度，而不是以模块数量建立表面复杂度。
