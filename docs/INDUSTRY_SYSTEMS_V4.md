# 大厂 Coding Agent 系统方向与本项目下一步

调研日期：2026-10-22。范围为官方产品文档、工程文章、开源仓库、模型卡与作者技术报告；招聘岗位由本轮另一份调研覆盖。这里区分三类证据：厂商公开的产品方向、厂商在特定实验中的观察、对本项目的实施建议。后两者不能自动相互推导。本文记录实验前的调研判断；随后完成的两模型云端诊断见 [v4 验证](VALIDATION_V4.md)，四次尝试均未产生补丁。

## 1. 当前主线是可验证的软件任务交付

大厂公开材料的共同指向是：理解仓库与需求，操作真实开发环境，修改代码，执行验证，保留可供审阅和继续工作的产物。在这个闭环内，长程上下文、工具协议、失败恢复、隔离执行和成本控制都是实际问题。API 只是模型的接入方式；是否使用多 Agent、RL 或某个框架，不能单独说明项目深度。

| 官方来源与时间 | 公开建设方向 | 对本项目的启示及边界 |
|---|---|---|
| [OpenAI：Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)，2026-08-19 | 开放的 harness 管理会话状态、工具执行、进度、失败、运行边界和跨轮工作；CLI、SDK、app-server 对接不同工作流。 | 执行循环和状态语义本身值得认真实现。开源 harness 与模型服务分开，不能把开放代码理解为免费获得前沿模型。 |
| [TRAE：Introducing The New SOLO](https://www.trae.ai/blog/new_solo_beta_0331)，2026-03-31 | Code Mode 中执行并迭代代码；工作区连接文件、上下文和任务历史；云端可以后台并行执行任务，结果供用户检查。 | 产品目标包括持续工作和可审查产物。并行独立任务不等于每道修复题都需要多个互相讨论的 Agent。 |
| [ByteDance Seed2.1 发布](https://seed.bytedance.com/en/blog/seed2-1-officially-released-advancing-ai-productivity)，2026-06-23 | 将需求分析、功能实现、修复、环境搭建和结果验证视为完整编码任务，并强调真实工作流。 | 只会输出函数或工具调用格式，距离端到端交付仍有差距。这是厂商方向陈述，不能当作独立质量测量。 |
| [Anthropic：长程 Agent 的有效 harness](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)，2025-11-26 | 研究跨上下文窗口工作的连续性，以进度记录、版本状态和实际测试减少半成品与过早宣布完成。 | 摘要需要关联可验证的工作状态。该实验中的初始化/执行分工，不是我们的修复任务必须照搬的架构。 |
| [GitHub Copilot on GitHub.com](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github)，当前文档，访问于调研日 | 仓库研究、规划、后台修改、临时环境中的测试与检查、分支和 PR 工作流；会话日志支持继续工作与审阅。 | Patch、验证日志、结束原因应形成一个交付单元。日志可读不代表代码正确，仍需测试与代码审阅。 |
| [Qwen3-Coder-Next 技术报告](https://arxiv.org/abs/2603.00729)，2026-02-28 | 在可执行环境中合成可验证编码任务，利用环境反馈开展中期训练与 RL；模型面向 coding agent。 | 后训练的价值依赖任务、环境、奖励和数据。论文里的规模与训练配方不能直接套到单卡项目。 |

这不是一份厂商排名。上述材料的任务、模型、资源和评估方式不同，因此不摘取宣传榜单数字来证明谁更强，也不把某产品的介绍当作本项目已有的能力。

开源实现中，[ByteDance trae-agent](https://github.com/bytedance/trae-agent) 提供可检查的工具和轨迹机制；其[评测说明](https://github.com/bytedance/trae-agent/blob/main/evaluation/README.md) 将仓库任务、运行环境、补丁与独立评分连接起来。它适合作为接口和评测实现的参考，但不能视为 SOLO 商业产品全部内部实现。以后运行参考框架时，应固定 commit、模型、提示、资源和任务集合；不能只安装同名包就声称复现。

## 2. 有技术深度的系统应该能回答哪些问题

下面是从这些公开方向推导出的工程检查表，不是声称所有厂商都采用同一内部架构。

| 层次 | 实际问题 | 我们能展示的证据 |
|---|---|---|
| 交互协议 | 谁提出动作，哪个工具返回了什么，下一轮是否误读历史？ | 原始模型消息、角色、动作和观察配对；同模型协议对照。 |
| 仓库理解 | 是否读到了相关实现、测试配置和调用关系？ | 访问文件范围、定位轨迹、未读取代码就修改的失败样本。 |
| 编辑和恢复 | 修改是否局部、可执行；工具报错后是否改变行为？ | Patch、语法/测试结果、无效编辑次数、重复错误率。 |
| 上下文与预算 | 保留的信息能否支持下一步；摘要成本是否划算？ | 实际 tokenizer 计量、预算遵守、信息删除记录、成功率与成本曲线。 |
| 环境与验证 | 模型失败、环境失败和评分失败能否分开？ | 固定镜像、基准提交、官方评分记录、正负对照。 |
| 长程状态 | 中断、压缩、恢复后是否知道已完成与未完成的事项？ | 文件版本、已执行测试、失败原因和未解决事项的可追溯记录。 |
| 交付与协作 | 人能否理解并继续这次修改？ | 变更说明、测试证据、完整轨迹、可重新执行的命令。 |
| 学习闭环 | 什么行为应被训练，奖励是否可信，提升能否泛化？ | 有效 rollout、数据来源与切分、冻结验证集、训练前后公平对照。 |

预算不仅是 token。Anthropic 的 [Infrastructure noise](https://www.anthropic.com/research/infrastructure-noise)（2026-02-05）说明执行资源与超时配置可能改变 Agent 评估结果。因此，本项目比较至少应记录 CPU/RAM、执行超时、镜像、并发、模型加载之外的耗时；有些环境错误应单列，不能全部编码成模型奖励 0。

“更复杂的 harness 必然更好”没有得到这些材料支持。Anthropic 的 [Harness design for long-running apps](https://www.anthropic.com/research/harness-design-long-running-apps)（2026-03-24）讨论逐个去除组件，并说明模型变化后部分分解与评审机制可能变成额外成本。其应用生成案例不能直接证明我们应该使用同样的规划器、生成器、评审器。对我们的启示是：先固定模型和任务，观察轨迹，再逐项验证机制。

## 3. 当前项目的首要问题还不是复杂规划或 RL

依据仓库中的 [VALIDATION_V3.md](VALIDATION_V3.md)，v3A 的真实开发任务没有成功修复，部分运行用很短的整文件写入破坏源码；v3B 换成局部编辑后仍提交空补丁。运行结束、补丁非空、花费较少分别只是过程指标，不能替代修复成功。

本次研究时检查 `src/budget_agent/context.py`，旧接口将历史动作和观察组合成 `Action: ... / Observation: ...` 文本，并统一放入 `user` 消息。结合此前无效续写的轨迹，这是值得检验的协议问题；目前只能称为候选原因，尚未证明它导致了失败。

建议下一版只回答一个先决问题：**保留模型动作与环境观察的角色差异，能否让同一个模型更稳定地完成读取、局部编辑和验证？**

可执行的最小干预如下：

1. 保留旧 transcript 协议作为对照；增加成对的历史表示，模型提出的动作作为 `assistant` 内容，工具观察作为后续环境反馈。当前纯文本工具接口可以用明确标记的 `user` 观察，暂不伪装成原生 function calling。
2. 在裁剪最近历史时保留动作与观察的配对关系，正确重新计量聊天模板 token；被截断的观察明确标记。避免修复角色时同时更换上下文算法。
3. 对原生工具接口另行处理 `tool_calls`、调用 ID 和对应 `tool` 返回；只有后端、模板、解析器完整支持时再启用。不能把文本 JSON 换成一个角色名就称为原生工具调用。
4. 首轮仍固定既有 7B 模型、同一开发任务、局部编辑工具、输出上限和累计预算，比较旧协议与新协议。它是定位问题的开发实验，不能成为最终 benchmark 成绩。
5. 保留失败，查看无效动作、重复相同错误、成功局部编辑、测试执行和补丁结果。即使协议错误减少，若最终修复仍失败，也要据实记录。

这轮不同时加入“自动重试若干次取最好”“隐藏格式修复”“扩大预算”“多 Agent”“换强模型”。否则一次成功也很难解释来自哪项变化。预算内允许的错误反馈应统一定义，不能只给改进组额外机会。

## 4. 单张 RTX 4090 的参考模型选择

首轮协议对照继续使用现有 `Qwen2.5-Coder-7B-Instruct`，是为了定位变量；它不代表 2026 年前沿模型。完成协议检查后，建议只增加一个独立参考候选。下表是兼容性与资源判断，尚未对这些候选运行本项目任务。

| 候选 | 官方可核验信息 | 建议用途 |
|---|---|---|
| [Qwen/Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) | 4B 因果语言模型，仅 non-thinking；示例使用 `AutoModelForCausalLM` 和聊天模板，模型卡提供工具使用指导。 | 优先作为低适配成本的独立参考。先单路推理、8K 上下文、固定总预算。它可能改善指令/工具遵循，也可能在真实修复上不如原 7B；必须实际测量。 |
| [Qwen/Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B) | 当前模型卡使用多模态加载接口；默认 thinking。服务示例使用 `qwen3` reasoning parser 和 `qwen3_coder` tool parser，并提供关闭 thinking 的配置。 | 后续的较新模型参考。须独立验证依赖、模板、解析和计量；不能认为当前纯文本 `AutoModelForCausalLM` 后端直接替换名称即可。 |

资源估算：4B 参数按每个 BF16 权重 2 字节计算，权重约 8GB（十进制），还要加 KV cache、运行时、工作空间和可能的额外模块；这是算术估计，不是实测峰值显存。24GB 单卡以 batch 1、有限上下文开展推理诊断有合理可行性，但仍以服务器实测为准。模型卡写有长上下文能力，不等于在 24GB 显存上能开满该长度，也不等于长上下文在固定预算内一定更有效。

不要按 MoE 的“激活参数量”选择显存。例如上述 Qwen3-Coder-Next 报告中的总参数为 80B、每次激活 3B；BF16 全权重仅按总参数估算即约 160GB。单卡不能因为“3B active”就按 3B 权重规划。量化或 CPU offload 会引入新的速度、精度和依赖变量，当前优先级低。

如果测试 thinking 模型，生成的思考 token 也必须计入总预算；最终动作短不意味着本次调用便宜。比较中要记录推理模式与参数。现在不承诺这两个候选是所有可用模型中的最优，也不推荐为了追逐型号放弃已有可复现基线。

## 5. 接下来值得投入的技术主线

项目定位建议保持为：**固定推理成本下，面向真实仓库修复的可靠交互与上下文管理评测。** 可见成果应是一个能解释失败、验证改动和复现实验的系统，加上一个有边界的改进结论。

| 顺序 | 要解决的问题 | 继续下一步需要什么证据 |
|---|---|---|
| A. 协议诊断 | 历史角色、工具观察与编辑错误是否被正确理解？ | 同模型同预算对照；保存完整轨迹和失败，不预设必须提升。 |
| B. 能力定位 | 失败主要来自模型、工具接口还是任务环境？ | 增加独立模型参考与多个事先确定的开发任务；环境有已知正确/错误补丁对照。 |
| C. 上下文研究 | 保留哪类工作证据最有用？ | 在能产生有效修复的基线上比较 recent 与一种证据保留策略；摘要和检索均计费。 |
| D. 确认实验 | 开发结论在未调参任务上是否成立？ | 冻结任务、参数和实现后，运行未参与开发的确认集合，报告样本量与不确定性。 |
| E. 后训练 | 能否让模型更少犯协议/编辑错误，或更好使用预算？ | 可信轨迹、训练/验证分离、可靠奖励、未训练基线；随后才评估 SFT 或 RL。 |

C 阶段最合适的具体研究对象，是**保留“定位证据、编辑结果、测试结果、当前文件版本”的上下文选择**。它比抽象地说“加记忆”更容易定义和检验：保留的信息是否减少重复读取、无效编辑和过时结论？同样预算下是否改善最终修复？如果任务过短，历史从未成为瓶颈，就不应据此宣称长程管理有效。

开发集可逐步扩展到多个仓库、多个任务；首批 5–10 个任务只适合发现稳定故障，仍不足以支持广泛胜率结论。最终比较需要预先说明任务选择、模型版本、推理模式、预算、重复次数、环境和异常处理。不能在看完结果后剔除困难题，不能将已有反复调试的 `astropy__astropy-12907` 当作未见测试任务。

## 6. RL 与工程工作的关系

Qwen 的 [Qwen3-Coder 官方说明](https://qwenlm.github.io/blog/qwen3-coder/)（2025-07-22）把代码执行反馈、长程工具交互训练和工具协议适配联系起来。这说明 RL 可以训练执行策略，也说明仅有一次 API 调用或一个奖励函数远远不够。对当前项目，更迫切的是获得可靠的环境交互与可辨别的结果。

将来开展 Agentic RL，至少需要：

- 可训练的开放权重和明确的训练目标；调用闭源 API 本身不能更新供应商模型权重，但可用于收集示范或评估。
- 可重复执行的任务环境，以及区分编译/测试失败、环境失败、解析失败和空补丁的奖励记录。
- 经过检查的 rollout 数据；错误评分产生的样本不能当作成功训练证据。本仓库既有 v2 无效尝试继续保持无效标记。
- 训练、开发、确认任务之间的隔离，以及按相同推理预算比较的未训练基线。
- 明确计算 rollout、模型更新、验证三部分的时间和显存；单卡小模型试验可以验证局部学习问题，不能等同于复现大厂长程训练规模。

在这些条件成熟前，多 Agent 协作和 RL 都容易增加难以解释的变量。下一版最值得交付的是“协议对照 + 正确计量 + 官方评分 + 失败归因”这一最小闭环。其职业价值来自工程判断和可信证据；是否获得岗位认可还取决于实际结果、代码质量、基础能力和面试表达，本调研不能保证。

## 7. 证据局限

- 产品材料说明公开定位与功能，不公开全部训练数据、内部 harness 或线上成功率；不能据此逆向推定企业内部实现。
- 工程文章和作者报告中的观察依赖各自模型与任务。没有将它们的数值当成本项目的可比结果。
- 当前网页与模型卡可能更新。真正执行时应另存模型 revision、代码 commit、依赖和实验配置；本次访问并没有固定所有上游快照。
- 上述候选表形成时两个参考模型均未运行。随后 v4 已验证 Qwen3-4B-Instruct-2507 的固定版本；Qwen3.5-4B 仍未运行，24GB 可行性与峰值显存仍不是实测承诺。
- 本项目现有真实任务证据仍以少量开发诊断为主。方案提出的收益全部待验证，单题失败或成功都不能支撑总体策略排名。
