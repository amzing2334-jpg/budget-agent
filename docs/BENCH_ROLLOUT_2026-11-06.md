# Rollout 吞吐与并发（2026-11-06，A100-40GB）

原始数据在 [`docs/data/bench_rollout_2026-11-06.json`](data/bench_rollout_2026-11-06.json)，驱动脚本是 `scripts/autodl/bench.sh`，测量逻辑在 `scripts/bench_rollout.py`。

## 设置

- **硬件与服务**：一张 A100-PCIE-40GB，vLLM 0.33，模型为 Qwen2.5-Coder-7B-Instruct。
  - `max_model_len` 32768，`gpu_memory_utilization` 0.88。
  - 开启前缀缓存，`max_num_seqs` 64。
- **harness**：配置与第一轮相同（`configs/swesmith-vllm.toml`）：`recent` 策略，最多 30 步，temperature 0.7，单次输出上限 2048。agent 的命令以 `nobody` 用户执行。
- **任务**：训练集清单的前 64 题，来自 3 个仓库（voluptuous 24 题，textfsm 24 题，isodate 16 题）。
- **流程**：每种 worker 数下，每题跑 1 次。按 8 → 16 → 32 → 64 的顺序依次运行，后面的设置可能复用前面留在前缀缓存里的内容。

## 结果

| worker 数 | 尝试/小时 | 生成 token/s | prompt token/s | 前缀缓存命中率 | GPU 利用率 | 单次尝试 P50 | P95 | 模型调用之外的时间占比 |
|---|---|---|---|---|---|---|---|---|
| 8 | 1100 | 268 | 31,398 | 0.89 | 97% | 23 秒 | 55 秒 | 10.4% |
| 16 | 1170 | 310 | 36,997 | 0.89 | 95% | 37 秒 | 75 秒 | 7.2% |
| 32 | 678 | 167 | 23,588 | 0.77 | 96% | 116 秒 | 194 秒 | 4.3% |
| 64 | 1197 | 308 | 33,209 | 0.88 | 96% | 105 秒 | 140 秒 | 10.5% |

## 发现

1. **Rollout 由 prefill 主导。**
   - prompt token 是生成 token 的 108 到 141 倍。前缀缓存命中率约 0.88。
   - 扣除命中后，每秒真正需要 prefill 的 token 约 3,500 到 4,000 个，而 decode 只有约 300 个。
   - agent 每一步都要把越来越长的上下文重新送进模型，生成的却只是一个很短的工具调用。
2. **8 个 worker 时 GPU 已经饱和。**
   - GPU 利用率在 95% 到 97% 之间。从 8 个到 64 个 worker，吞吐都在每小时 1100 到 1200 次左右。
   - 并发增加以后，单次尝试变慢了：P50 从 23 秒变成 105 秒。增加的只是排队时间，吞吐没有提高。
3. **环境不是瓶颈。** 模型调用之外的时间（工具、测试、评分）只占 4% 到 11%。这一点和依赖 Docker 的 SWE-bench 环境不同：这组任务用每个仓库独立的 venv，测试几秒就跑完。
4. **32 个 worker 是一个异常点，原因没有查明。**
   - 每种设置只跑了一次，每次 64 题，测到的"尝试/小时"其实是这批任务的完成时间（makespan）。32 个 worker 正好分成两波，每一波又被长尾拖住。
   - 同步 RL 每一步正是"等一批 rollout 全部跑完"，所以这个量本身有意义。但要分清异常和噪声，需要重复测量。

## 对 RL 的含义

- 同步 GRPO 每步 64 次尝试，在这张卡上 rollout 约 190 到 210 秒（worker 数 ≥ 8，32 除外）。第二轮的实测时间见 `docs/EXPERIMENT_GRPO_ROUND2.md`。
- 要更快，应该从以下方向下手，而不是增加并发：
  - 缩短上下文（上下文策略）；
  - 提高前缀复用；
  - 改成异步 rollout 或 partial rollout，避免等长尾；
  - 增加推理卡。

## 局限

- 每种设置只测了一次。只有 3 个仓库。同一批任务按顺序重复使用，前缀缓存是热的。
- nvidia-smi 的"GPU 利用率"表示采样时有没有 kernel 在运行，不代表 SM 的占用率。
- vLLM 的 prompt token 计数里包含命中缓存的 token。
