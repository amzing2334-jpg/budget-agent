# 第一轮：SWE-smith 本地任务上的拒绝采样微调（RFT）

本协议在运行前冻结，写于 2026-11-06。运行后只追加结果，不修改下面的判据。

## 问题

用教师模型在训练仓库上采样，只保留独立 verifier 判定通过的轨迹，用它们对学生模型做 LoRA SFT。要回答的问题是：学生模型在**没见过的仓库**上，修复率是否提高？

## 对象

- **任务**：来自 SWE-smith 数据集的 12 个纯 Python 仓库。仓库按固定种子 20261105 划分：8 个训练，4 个留出评测（funcy、tomli、parse、tinydb）。每个仓库按同一种子最多选 24 个实例，筛选条件是有问题描述、补丁只改 1 个文件、1 ≤ F2P ≤ 20、P2P ≤ 2000。选择脚本和结果见 `scripts/build_swesmith_local.py` 的输入。
- **准入**：一个实例要进入任务集，必须同时满足：
  - 干净代码连续运行 2 次，F2P 全部通过；
  - 打上 bug 补丁后，至少 1 个 F2P 失败；
  - 两次运行结果完全一致；
  - 每次运行都断言被测包是从当前树导入的；
  - 环境导致的 P2P 丢弃不超过 20%。
- **执行**：harness 不变，与评测共用同一条代码路径（`run_task`）。配置见 `configs/swesmith-vllm.toml`：`recent` 策略，最多 30 步，temperature 0.7。agent 的命令以 `nobody` 用户执行。评分只应用可编辑源文件的改动（`grading_scope: editable_only`）。
- **模型**：
  - 教师：Qwen2.5-Coder-7B-Instruct。
  - 学生：Qwen2.5-Coder-1.5B-Instruct。两者同一系列，tokenizer 和 chat template 相同。
  - 都用 vLLM 服务，`max_model_len` 为 32768。

## 流程

1. 教师在训练任务上每题采样 4 次。每题最多保留 2 条通过的轨迹，作为 SFT 数据。
2. 学生基线：在留出任务上每题采样 4 次。
3. LoRA 训练：r = 64，α = 128，学习率 1e-4，2 个 epoch，最大长度 16384，只对 assistant 回复计算 loss。
4. 训练后的学生：在留出任务上每题采样 4 次，配置与第 2 步完全相同。

## 判据（冻结）

- **主指标**：留出集上的 pass@1，即每题 4 次采样的通过比例，再对题目取平均。
- **检验**：训练后减训练前，按题目做配对 bootstrap，10,000 次重采样，计算 95% 置信区间。
- **结论规则**：
  - 区间下界大于 0，结论为"在留出仓库上有提升"；
  - 区间包含 0，结论为"未检测到提升"；
  - 区间上界小于 0，结论为"变差"。
- **次要指标**（只做描述，不做推断）：训练集上的 pass@1、无效动作比例、平均步数、状态分布、被忽略文件的统计、教师在留出集上的 pass@1（每题 2 次，作为参照）。
- **防作弊检查**：逐条检查训练后通过的补丁。如果出现改测试、读取评分通道、`os._exit` 之类的模式，该条记为可疑，并另外报告剔除可疑样本后的结果。

## 预算

- GPU 估算：A100-40GB 约 4 小时，其中教师采样 1.5 小时、学生两次评测共 1 小时、训练 0.3 小时，其余为余量。
- 费用：约 13 元（3.28 元/小时）。实例在用户的 AutoDL 账户上，余额约 50 元。

## 已知局限

- 只有 1 个随机种子，也只有 1 个教师和 1 个学生。
- 留出仓库只有 4 个，结论只适用于这 4 个仓库。
- SWE-smith 的 bug 是合成注入的，难度分布与 SWE-bench 不同。
- RFT 不是 RL。本轮验证的是数据和训练闭环，不代表策略优化方法的效果。

## 追加：训练脚本的实现变更（2026-11-06 12:52 UTC，训练阶段开始前）

- **改了什么。** 只改了 `scripts/train_sft_lora.py` 计算 loss 的方式。
  - 原来调用模型自带的 loss，每个位置都要算一遍覆盖整个词表（约 15.2 万）的 float32 logits。
  - 现在只在预测训练 token 的位置计算 logits（`logits_to_keep` 传入位置索引），再对这些位置的交叉熵取平均。
- **为什么改。** 11:45 UTC 左右，用当时已解出的 29 题生成了 487 条 SFT 样本，测得以下分布：
  - 长度：P50 为 3361 个 token，P90 为 10377，最长 16214。超过 12k 的有 22 条，另有 15 条超过 16384 被丢弃。
  - 每条样本平均只训练 43.6 个 token，占全部 token 的 0.97%。
  - 按原写法估算显存：16k 长度的样本在反向传播时，logits 及其梯度约占 28 GiB。加上权重、LoRA 和优化器状态，峰值约 33 到 34 GiB。A100-40GB 的可用显存约 39.4 GiB，存在显存不足的风险。
- **为什么不影响判据。**
  - 新写法在数学上与原 loss 完全相同。冻结的超参数都没有变，包括 r、α、学习率、epoch 数、最大长度，以及只对 assistant 回复计算 loss。
  - 验证在服务器 CPU 上进行，库版本与 GPU 环境相同：torch 2.14、transformers 5.20.2、peft 0.21.2。用一个随机初始化的小 Qwen2 模型，分别在带 LoRA 和不带 LoRA 两种情况下比较，loss 和全部可训练参数的梯度与原写法相差都在 1e-6 以内（`tests/test_sft_loss.py`）。
- **替换时间。**
  - 12:52 UTC 替换。当时第一轮正在做学生基线评测（370/384），训练阶段还没有开始。
  - 替换前，服务器上的文件与 `main@59f1aca` 一致，sha256 前 16 位为 `a8ecfa372fff893b`。替换后为 `73a9f7d8ad4de351`。
  - harness 包没有改动，包级哈希仍为 `3894d873f4c97b73`。

## 追加：第一轮结果（2026-11-06 13:59 UTC 完成）

**主指标（冻结判据）。**
- 留出集：funcy、tomli、parse、tinydb 四个仓库，共 96 题，每题采样 4 次。
- pass@1：训练前 0.26%（384 次里 1 次通过），训练后 6.25%（384 次里 24 次通过）。
- 差值 +5.99 个百分点。按题目做配对 bootstrap（10,000 次重采样），95% 置信区间为 [+2.86, +9.64]。
- 区间下界大于 0，按冻结规则，**结论为"在留出仓库上有提升"**。
- 14 题变好。1 题变差，就是训练前唯一解出的那一题，训练后 4 次都没解出。其余 81 题不变。两边都没有未评分的尝试。

**防作弊检查。**
- 训练后在留出集上通过的 24 个补丁，逐条人工检查过。
  - 每个补丁都只改 1 个源文件，内容是把注入的 bug 改回来。例如去掉多余的 `reversed(...)`、`[::-1]` 或 `- 1`，或者把 `TOMLDecodeError` 的基类 `ValueError` 补回去。
  - 没有修改测试，没有被忽略的文件，没有触发任何补丁信号，也没有读取评分通道。
- 六个采样池里，通过且带补丁信号的尝试都是 0 个。所以"剔除可疑样本后"的结果与主结果相同。

**次要指标（只做描述，不做推断）。**

| 指标 | 学生训练前 | 学生训练后 | 参照：教师 7B |
|---|---|---|---|
| 留出集 pass@1 | 0.26% | 6.25% | 7.29%（每题 2 次） |
| 留出集 pass@2 | 0.52% | 10.07% | 11.46% |
| 留出集 pass@4 | 1.04% | 14.58% | — |
| 留出集解出题数 | 1/96 | 14/96 | 11/96 |
| 留出集 `edit_file` 成功率 | 10.4%（93/895） | 49.5%（792/1599） | 51.4%（474/922） |
| 留出集平均步数 | 15.1 | 19.1 | 17.1 |
| 留出集状态（finished / stuck / max_steps） | 47 / 206 / 131 | 42 / 215 / 127 | 16 / 127 / 47，另有 2 次模型错误 |
| 训练集 pass@1（每题 1 次） | 0/192 | 2.65%（189 道配对题里 5 题；另有 3 次未评分） | 7.16%（每题 4 次） |

按仓库分：

| 仓库 | 学生训练前 | 学生训练后 | 教师（每题 2 次） |
|---|---|---|---|
| funcy | 0/96 | 7/96（3 题） | 4/48（3 题） |
| parse | 0/96 | 6/96（4 题） | 3/48（3 题） |
| tinydb | 1/96 | 10/96（6 题） | 6/48（4 题） |
| tomli | 0/96 | 1/96（1 题） | 1/48（1 题） |

- 提升分布在全部四个留出仓库，不是集中在某一个仓库。
- 变化主要来自编辑是否成功。训练前，学生的 `edit_file` 只有 10.4% 能对上锚点，多数尝试卡在重复失败的编辑上。训练后成功率是 49.5%，与教师的 51.4% 相当。
- 主动结束的次数前后接近（47 和 42），但结束时补丁的正确率从 1/47 升到 24/42。也就是说，SFT 主要改善的是定位和修改的正确性，而不是终止行为。
- 训练集上的数字只做描述，因为其中 33 题的成功轨迹被用作了 SFT 数据。

**SFT 数据与训练。**
- 教师在训练集上采样 768 次，通过 55 次（7.16%），覆盖 33 题。每题最多取 2 条轨迹。
- 得到 658 条样本，全部是"只训练最后一个回复"的形式，其中 619 条长度不超过 16384。
- 训练 155 步，用时 1010 秒，显存约 11.8 GiB，参与 loss 的 token 有 25,522 个。loss 从 0.21 降到 0.095。

**未评分与模型错误。**
- 未评分共 9 次，全部是 verifier 跑满 300 秒（教师训练集 6 次，训练后学生的训练集 3 次）。按第一轮的语义，它们不计入 pass@k。之后的实验改为记作失败（PR #11）。
- 模型错误 5 次，这 5 次都有独立评分，按失败计。
  - HTTP 400 两次。原因是上下文超过了 32768：80000 的上下文预算按字节估算，而 gpxpy 的代码约 2.5 字节一个 token，字节预算限不住真实 token 数。其中一次，前一个请求的 prompt 已经有 32188 个 token。
  - 请求超时 3 次。
- 改进方向：按真实 token 计算预算，或者把字节预算降到约 64000。这会改变 agent 的上下文行为，所以留到下一轮之前再做。

**耗时与费用。**

| 阶段 | 用时 |
|---|---|
| 教师：训练集采样 / 留出集采样 | 57 / 17 分钟 |
| 学生基线：留出集 / 训练集 | 23 / 5 分钟 |
| SFT 训练（含合并和保存） | 17 分钟 |
| 训练后学生：留出集 / 训练集 | 25 / 17 分钟 |
| 启动 vLLM 三次 | 共 4 分钟 |
| **合计** | **2.79 GPU 小时，约 9.2 元**。协议估算为 4 小时、13 元 |

- 长尾：训练后学生的训练集采样里，最后一次尝试的 verifier 跑了很久，GPU 空等了大约 5 分钟。
- 干净代码上测试的 P95 是 2.2 秒，而 verifier 统一用 300 秒超时。在 RL 里，一整批 rollout 要等最慢的那一次尝试，所以下一步要按每题准入时测得的耗时设定超时，例如取 30 秒和干净耗时 10 倍中的较大者。

**偏差。** 前面各节已有记录：
- Python 是 3.12，不是协议写的 3.10；
- 训练脚本的 loss 实现有变更，数学上等价；
- 启动阶段发生过一次事故。

**局限。** 这一轮的结论只适用于以下范围：
- 1 个随机种子，1 个教师和 1 个学生，4 个留出仓库；
- SWE-smith 的 bug 是合成的，通过的补丁大多只是一行的还原；
- 学生的绝对水平仍然很低（6.25%）；
- RFT 不是 RL。
