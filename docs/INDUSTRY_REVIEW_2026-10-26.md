## 3. 从现有原始结果确定优先级

依据：[v5 失败分析](../runs/v5-followup-20261022-01/CLOUD_FAILURE_ANALYSIS.md)、[v5 后续验收](VALIDATION_V5_FOLLOWUP.md)。历史原始结果保留不动。

- 同源码 recent/mask 配对仍是同一道已知开发题。mask 的 9 次文件读取累计返回 479 行，其中唯一行 317、重复覆盖 162；增加的浏览没有产生编辑、测试或补丁。
- `mask × direct/budget-aware` 后续配对仍为空补丁。笼统提醒“注意预算、开始修复”尚未获得有效结果。
- 外部 mini-SWE 参考也出现合法但无实际改变的编辑命令；工具返回成功不等于工作区变化，更不等于修复正确。
- 官方空补丁记录为未执行测试；不能把它写成已经跑过测试并得到修复失败率。

| 优先级 | 项目问题 | 本轮可验证交付 | 不足以支持的结论 |
|---|---|---|---|
| P0 | 已知停滞只在事后暴露；模型仍会耗尽预算 | 将可核对的重复动作、重复文件覆盖、无修改状态用于有边界的运行时反馈或停止；保留策略开关、触发证据与真实结束原因 | 停止更早不是修复率提高；历史回放不能模拟模型收到新反馈后的行为 |
| P0 | 缺少有效修复的模型/交互参考配置 | 准备固定配置、受控任务和独立评分入口；后续获准云端或 API 实验后验证能否产生通过测试的非空补丁 | 仅换模型后得到成功，不能归因于上下文或停滞策略 |
| P1 | 真实效果证据集中于单一道已知题 | 先锁定任务集合、预算和唯一尝试规则，再作同模型单因素对照；报告所有任务及未评分项 | 不能把自适应开发尝试当独立最终测试集，也不能把多次重试当多道题 |
| P2 | 尚无可信训练数据和训练收益 | 在有效修复之后建立轨迹质量筛选、来源与切分，再考虑 SFT/偏好/RL | 当前无效旧 GRPO 更新、成功工具调用和 CPU 测试均不是 RL 收益证据 |

本轮最值得深入的技术问题是：**运行时能否在不误判正常读取、必要复核和版本变化的前提下，识别无进展的重复交互，并把干预成本、触发证据和停止原因交给评测。** 这是可在 CPU 上验证的软件契约；最终是否帮助模型恢复，必须使用新的真实模型轨迹验证。

实现宜直接：复用已有事件和版本记录；把策略作为独立实验因素；避免无条件自动重试、强制编辑、针对 Astropy 题目的硬编码提示，以及把读过的源码永远禁止再读。源码在工作区未变时仍可能已被上下文裁剪，重新获取信息有时是合理行为。

## 4. 下一轮真实模型验收门槛

1. 先检查执行环境和独立评分正负对照，确保测试确实执行，且评分私有信息未进入 Agent 输入。
2. 找到至少能完成开发题修复的参考配置，保留原始请求、补丁、测试和全部成本；首次成功只作为能力诊断，不能声称泛化。
3. 固定多个开发任务、模型版本、预算与环境，比较未干预策略和候选策略。不同模型或 harness 分组分析。
4. 同时报任务成功、空补丁、非空但未通过、基础设施异常、预算/停滞结束、有效编辑与测试行为。记录干预误报，不能只报节约的 token。
5. 若效果仍无改善，应优先重新判断模型能力、工具契约和任务难度，而不是继续叠加提示与模块。

此处是验收计划，不是已完成实验。本轮调研没有调用模型、租卡或训练；任何真实实验结果由运行产物另行证明。

## 5. 每四小时评估的持续标准

每轮先读取当前源码、最近运行与待验证假设，再核对少量直接相关的官方岗位和工程来源。记录观察日期与来源日期，明确相对上轮是否有实质变化；来源不可读时保留不确定性。招聘信息用于判断能力缺口，不用于强制添加关键词功能。

每轮选择一个证据最充分的瓶颈，写清可验收的改进、成本和局限，再修改代码、运行相关 CPU 检查并审查差异。有效改进可以是消除一个错误判定、验证一条失败机制或删掉无效复杂度，不要求以更多代码和更多依赖体现进展。

云端训练、付费模型和新租用资源不因定时任务而自动获得预算；本机继续只做代码与 CPU 软件检查。没有真实模型结果时，报告应明确“软件机制已验证，模型效果待验证”，并推进不依赖算力的工作。
