# Coding Agent 项目方向与六周准备方案

调研日期：2026-10-22，北京时间。本文区分行业证据、当前已知事实、准备实施的实验和未来目标；不是结果报告，也不承诺录取。代码完成情况应以实际运行记录为准，不能把本文的计划写成简历中的既成成果。

最新结果见 [v5 后续验收](VALIDATION_V5_FOLLOWUP.md)：真实内部/mini-SWE 尝试及两对适应性实验共七次，均未产生补丁；观察压缩扩大了动作机会，预算提示仍未推动有效编辑。下一里程碑必须先获得“失败复现—有效编辑—独立验证”的实际能力证据，继续调上下文超参数和开展 RL 暂不优先。实施背景见[笔记研读后的 v5 方案](IMPLEMENTATION_V5.md)。下文保留较早的研究规划，不能把候选方法当作已有收益。行业来源见[直接 Coding Agent 岗位要求](INDUSTRY_REQUIREMENTS_V4.md)和[大厂系统方向](INDUSTRY_SYSTEMS_V4.md)。

## 推荐定位

建议把项目定位为：**固定推理预算下的仓库级 Coding Agent：可回溯上下文管理与可信修复评测。** 以 Agent 系统、评测和数据工程为主体，围绕一个可验证的上下文改进建立算法深度，再依据结果决定是否开展后训练。

这个定位适合当前处境：西工大计算机硕士在读，有网络协议研究背景，但 Python、PyTorch 和深度学习项目基础仍需补齐，算力以按需短租单卡 RTX 4090 24GB 为主；此前实例已经归还。网络协议研究中对成本、延迟、状态、调度、异常和实验对照的理解可以迁移到 Agent 系统；无需强行把网络协议问题塞进代码修复任务。

本项目的目标是拿出招聘方可以检查、复现、追问的工作：真实问题、合理基线、明确改进、可信结果、失败解释和清晰代码。它可以增强 Agent 算法工程、Coding Agent 工程、Agent 评测或训练系统岗位的竞争力。它不能独立保证大厂面试或录取，也不能代替编程、数学、系统基础和对自己代码的理解。

## 三种路线的取舍

| 路线 | 当前能获得的有效证据 | 主要限制 | 决策 |
|---|---|---|---|
| 真实仓库上的预算与上下文改进 | 实际模型补丁、官方评分、成本与失败归因、受控对照；工程与实验能力可以逐步增加 | 需要把环境和计量做对；方法不一定胜过简单基线 | **作为主线。** 先验证一个任务，再建立有规模的比较。 |
| 继续在少量合成题上直接做 RL | 能理解 rollout、奖励、advantage、动作 token 对齐和参数更新 | 任务过于简单或同模板；容易把协议学习当代码能力，把评分错误当学习信号 | 保留为学习和单元验证用途，不作为求职项目的核心成绩。 |
| 从基础模型训练切入 | 小规模复现可以帮助理解训练流程 | 高质量数据、算力、训练稳定性和评测成本远超现有条件；无法用单卡短租复现大厂规模 | 暂不作为主项目。先建立 Agent 系统与评测能力，再选择局部后训练问题。 |

“算法方向”不等于必须首先训练模型；“调用 API”也不等于没有技术深度。项目深度取决于解决了什么问题、怎样排除替代解释、证据是否支持结论。反过来，仅仅写了 GRPO 更新函数也不能自动让项目变成高质量算法项目。

## 当前项目真实做到哪里

在本轮规划开始时，现有材料支持以下判断：

- v1 已有 Agent 循环、预算核算、`full / summary / structured` 策略、Docker 工具执行、轨迹与报告。`structured` 已包含来源和代码版本相关的证据管理。它是实现基础，尚未证明优于强基线。
- 离线 smoke 使用预先写好的动作。云端 Docker 烟测已证明容器执行和独立评分链路可工作，不能据此报告 LLM 代码修复成绩。
- 现有 0.5B SFT 的合成题结果只支持小型课程上的协议学习与流程验证；同模板数值划分不能证明真实仓库泛化。
- `runs/learning-v2/grpo` 曾因评分解析错误产生虚假负奖励，相关更新已经判为无效。不能拿它证明有效 RL，也不能把 SFT 提升归因于 RL。
- 已准备 5 个 SWE-bench Lite 开发任务和补丁导出/官方评分回填接口。它们原本来自公开数据的 `test` split，但已经用于本项目开发，必须继续算作本项目 `dev`，不能再当最终独立测试集。

对应证据见 [项目说明](../README.md)、[v2 验证记录](VALIDATION_V2.md)、[实验协议](EXPERIMENT_PROTOCOL.md) 和 [云端配置记录](CLOUD_SETUP_FEATURIZE.md)。本轮新增代码、模型运行和官方评分的实际结果应另按原始产物报告；本文不提前填写结果。

## 本次真实任务证据后的优先级调整

本轮已经在云端固定 7B 模型上执行了一个既有 Astropy 开发任务的三策略诊断，并使用官方评分器。gold 与非空无关补丁对照能区分正确修复和未修复；实际 Agent 尝试没有产生有效修复：`recent` 无补丁，官方跳过评分；`structured` 与 `summary` 产生破坏源码的补丁，官方判定未修复。完整配置、token、轨迹和评分边界见 [v3 云端验证记录](VALIDATION_V3.md)。这不是策略收益或整体 benchmark 成绩。

共同的近端问题比上下文选择更明确：模型只读 317 行模块的前 100 行就尝试整文件重写，短输出预算导致 JSON 截断；后续短写入又删除了必要实现。两份非空补丁的轨迹还照用了不适配当前仓库的测试命令示例，未完成有效测试发现。因此，**先修正局部编辑接口和测试发现流程，再研究上下文；目前不扩大 RL。**

随后已完成唯一原文匹配的局部 `edit_file` 与去除误导测试示例后的单独一次 `recent` 诊断。该轮仍为空补丁：模型在收到匹配两处的错误后重复同一编辑，没有测试便结束。新增工具尚未产生成功修复证据；下一步先以固定错误现场对照当前模型和参考工具调用模型，定位错误恢复能力与交互协议瓶颈。这是工具与提示改动，不能把新旧差异归功于上下文。下文的证据失效粒度仍作为候选研究问题，顺序后移；六周计划的前两周应优先跨过这些实际暴露的门槛，再依据新证据安排后续工作。

## 必须面对的先行工作

**上下文压缩、结构化记忆和学习压缩时机都已有工作，不能把这些功能名称直接当创新点。** 两篇需要认真对照的直接来源是：

- [AutoCompact: Learning When to Compact Context in Long-Horizon Coding Agents](https://arxiv.org/abs/2610.02163)，2026-10-01 提交。论文把何时压缩、保留什么工作状态以及如何继续行动纳入策略，结合修正轨迹的监督学习与任务奖励 RL，并在真实软件工程基准上报告改善。我们不能仅凭“让模型学会压缩”宣称新方向，也不能把其论文结果当作本项目结果。
- [The Complexity Trap](https://arxiv.org/abs/2508.21433)，2025-08-29 首次提交，当前 v3 为 2025-10-27，作者来自 JetBrains Research 等机构。其在 SWE-agent 上比较上下文方法，发现简单 observation masking 可以显著节省成本，并达到与 LLM 摘要相当的修复率；还有混合方法。它直接反驳了“摘要更复杂，所以一定更好”的直觉。

现阶段合适的贡献是：对一个具体、已有方法尚需验证的失效机制做清楚的工程实现和受控分析。若以后想投稿，必须进一步说明相对这些强先行工作的实质差异，并用新证据检验。求职项目不必在一开始就承诺论文创新。

## 核心问题与可能推翻它的结果

拟检验的问题是：**固定模型、任务、工具权限和推理预算时，保留有来源、可检查时效的修复证据，是否比简单上下文处理提高真实仓库修复率，或者在相近修复率下减少资源消耗？**

候选失效机制包括：旧文件内容在编辑后仍被当成当前事实；关键失败输出被压掉；重复读取相同大段文件消耗预算；摘要遗失可定位的错误细节。这些是待验证解释，不是已经观察到的普遍结论。

**首个最小改进建议收窄为“编辑后的证据失效粒度”。** 现有 `context.py` 依据整仓库 revision 标记旧观察过期。后续可以只给 `read_file` 证据增加文件内容指纹：改了 A 文件，不应自动把未变化的 B 文件内容标为过期；测试和任意命令的结果仍保守按仓库变化处理，不臆测语义依赖。保持上下文选取规则不变，对比整仓库失效、文件级失效与 observation masking，检查同版本重复读取、实际 token、修复与回归结果。若只是标记变短导致 token 下降、masking 同样好，或节省重读却降低修复率，都不能支持原先的机制解释。这是尚未实现和验证的工程假设，不是已有结果或新颖性声明。

| 最强替代解释或反例 | 如何区分 |
|---|---|
| 简单 observation masking 已经足够，结构化策略只有复杂度 | 在同一执行器、模型和任务上直接比较，并报告额外维护与推理开销。没有稳定优势就保留更简单的方案。 |
| 获益来自更强模型、更高预算或更多重试 | 控制模型版本、累计预算和尝试数；模型更换另列实验，不能归功于上下文方法。 |
| 节省 token 是因为 Agent 更早失败 | 同时报告成功、完整失败成本和停止原因；不能只画平均 token 降低。 |
| 全历史基线因故意设小窗口停止，制造明显“提升” | 最近窗口和 observation masking 必须作为有竞争力的基线；`full` 只提供额外诊断。 |
| 7B 模型本身几乎不会修复任务，方法之间没有可辨别信号 | 先做开发集能力诊断。若多种基线都失败，先解决模型或工具协议问题，不开始比较上下文优劣或扩大 RL。 |
| 隐藏测试、标准补丁或开发时看到的答案泄漏 | Agent 仅接收 issue、合法仓库内容和自己的工具反馈；官方评分独立执行。开发用过的任务永远留在 dev。 |

如果观察到的瓶颈主要是模型知识或代码能力，应该调整模型与任务范围；如果简单方法同样好，就报告这个边界。不能为了证明最初方案正确而不断修改指标、排除失败题或挑选成功的随机种子。

## 真实任务与比较协议

先完成一个真实任务的诊断，再扩展开发集；完成开发后冻结正式评测。预注册可以只是清楚的任务清单与实验协议，不需要再建复杂的 manifest 系统。

**任务选择。** 当前 5 个任务用于开发。后续正式比较建议预先选择至少 50–100 个真实任务，并覆盖若干仓库；这是工作规模建议，不是“达到 50 题就足够”的万能标准。抽样规则、任务范围和仓库组成必须在看方法结果前确定。若问题专门研究长轨迹或大输出，应事先定义选择条件，并把结论限制在该范围。开发结束后不得再用正式评测结果调提示、阈值或策略；一旦用于调整，这一批任务就变成开发数据，确认需要新的未参与调整任务。

**数据边界。** 标准补丁、隐藏测试 patch、FAIL_TO_PASS、PASS_TO_PASS 和 hints 不进入 Agent 上下文。公开 benchmark 的任务即使没有用于本项目开发，也可能出现在模型训练数据中，不能将“本项目留出的测试集”写成“模型从未见过的数据”。某个仓库或环境不能运行时记录原因，不静默删除不利任务。

**必要对照。**

| 方法 | 定义与作用 |
|---|---|
| 最近窗口 | 保留必要的 issue、指令及最近完整交互；淘汰旧历史。作为简单、可运行的主基线之一。 |
| Observation masking | 保留行动等必要信息，将较旧的大段工具观察替换为简短标记；与整体丢弃历史区分开。 |
| 摘要 | 使用同一模型对旧交互总结；摘要输入和输出、调用时间都计入预算。 |
| Structured | 根据已观察的来源、代码版本、错误与修改信息安排上下文，允许按需重新读取；不得使用答案或评分内部信息。 |
| `full` | 不压缩的诊断基线，超窗明确停止；不能只战胜它就宣称方法有效。 |
| 官方 mini-swe-agent 参考 | 固定官方版本，尽量使用同一模型、任务与预算；工具、提示、终止逻辑仍可能不同，应单独说明。现有自写循环不是官方 mini-swe-agent 复现，未实际运行其代码时不能写“优于 mini-swe-agent”。 |

内部策略比较应该在同一执行器里只改变上下文策略。官方 mini-swe-agent 是外部参考，不应因为匹配了模型就称为只改变一个因素的实验。

**配对条件。** 每个任务以相同模型 revision、tokenizer、温度、最大动作数、单次输出限制、上下文窗口、累计输入加输出预算、工具权限、镜像和评分版本进行比较。同一任务的重复采样标签要配对；API 不支持 seed 时明确记录，不虚构精确可复现性。不同模型 token 数不是同等 FLOPs；使用同一模型的 token 预算也不能替代延迟与实际费用测量。

**主要指标。**

- 完整报告 attempted、graded、resolved、预算合规数量和未评分原因；没有官方评分不能宣称修复成功。
- 比较配对的修复率差异，同时报告累计输入/输出 token、模型调用数、端到端耗时和模型推理耗时。延迟区分首次模型加载、镜像准备与正常执行；不把冷启动开销悄悄删掉。
- 报告成功与失败尝试的总开销；单位成功成本用全部尝试成本除以成功数。无成功时该值无定义，不写 0。
- 云租卡费用与 API 费用分别核算；未知价格、隐藏计费 token、未知用量不能按零处理。超预算的运行即使通过测试，也不能算作有效的固定预算胜出。
- 对配对差异给出不确定性，例如按任务重采样的区间；同一任务的多个随机种子不是多个独立任务。跨仓库结论还应检查仓库相关性和分层结果。仓库很少时应明确外推限制。

**失败分类。** 至少区分环境/依赖/镜像失败、模型响应或协议失败、上下文超限、累计预算耗尽、搜索定位失败、重复探索、过期证据、错误修改、回归失败和评分尚未完成。标签应能指向轨迹片段。不能把网络下载错误作为模型奖励 0，也不能因为修复没有通过就推断它一定是上下文问题。

## 什么时候才值得做 RL

先获得真实模型在真实环境中的稳定轨迹和可信奖励，再决定训练对象。有效的训练问题可能是压缩时机、证据选择或后续修复动作，但必须先识别现有规则方法的限制。

开展 RL 之前应能回答：基础策略有多大成功概率；组内奖励是否经常有差异；评分错误和环境错误如何区分；训练与评测是否分离；SFT、无训练基线与 RL 是否分别评价；获得收益是更多采样还是参数更新造成。若整组都成功或都失败，标准组相对奖励没有有效区分信号，不能靠人为误标奖励制造更新。

后续训练应记录真实 rollout、动作 token mask、旧策略概率、advantage、梯度和参数变化，并对独立任务做训练前后比较。KL、ratio clipping 和优势归一化都要能解释；把配置里出现 `GRPO` 当作算法经验远远不够。任何训练只在获准的云端 GPU 执行。

## 六周准备路线

以下按每周约 15–25 小时的有效学习与项目时间规划，是工作顺序而非保证进度。基础比预计薄弱时应缩小实验范围或延长周期，不应跳过理解去补结果数字。

| 周次 | 项目工作 | 学生必须亲自掌握 | 可检查的产物 |
|---|---|---|---|
| 第 1 周：10 月 22–28 日 | 完成一个真实 dev 任务的模型执行、补丁导出和官方评分；梳理现有预算与上下文代码 | Python 模块、数据结构、异常与测试；Git diff；Linux 进程、路径和 Docker 挂载；逐步讲清 Agent 循环 | 一份自己注释的轨迹、一张执行流程图、一次独立定位并修复的小 bug |
| 第 2 周：10 月 29 日–11 月 4 日 | 扩展小规模 dev 任务，跑最近窗口和 masking 等基线；把任务/工具/评分错误分开 | tokenizer 与聊天模板、采样与终止、模型输出解析；真实 issue 如何变成可执行评测 | 固定 dev 清单、可复用运行命令、失败分类和至少数个完整案例 |
| 第 3 周：11 月 5–11 日 | 阅读两篇强先行工作，提出一个具体机制改进，在 dev 上验证；不同时增加多个独立功能 | 实验中的控制变量、替代解释、资源匹配；能解释为什么现有方法可能足够 | 一页问题假设、针对机制的最小实现、失败或改善的直接证据 |
| 第 4 周：11 月 12–18 日 | 开发结束后冻结正式任务与配置，运行预先确定的真实任务比较；完成外部官方 Agent 参考时单列 | 配对统计、方差、不确定性、样本相关性、公开数据污染与结论边界 | 全部运行记录、成功/资源曲线、配对结果和不利案例；不预设必须有正增益 |
| 第 5 周：11 月 19–25 日 | 按证据决定：有训练信号才做小规模后训练；否则继续定位模型或上下文瓶颈 | PyTorch autograd、交叉熵与 log-prob、LoRA、SFT、策略梯度、GRPO 的假设和限制 | 一个可解释的训练对照，或一份说明为何此时不应训练的技术判断 |
| 第 6 周：11 月 26 日–12 月 2 日 | 整理可复现入口、简洁技术报告与面试演示；复盘结果和局限 | 不看生成答案也能讲清代码；手写关键计算、现场改预算或定位失败；解释资源与方案取舍 | 诚实的简历条目、10 分钟演示、30 分钟技术深挖材料 |

**你需要亲自掌握，并能接受面试追问：**

- **Python、Git、pytest 与调试：** 能从失败轨迹复现 bug，写一个捕获该错误的测试，修改代码并解释 diff；能区分程序异常、模型错误和测试失败，不依赖助手替你定位。
- **Transformers、KV cache 与上下文成本：** 能沿 tokenizer、聊天模板、`generate` 讲清一次推理，解释 prefill/decode、显存中权重与 KV cache 的区别，以及重复发送历史为什么继续消耗 token；能说明实际后端是否复用缓存，不能默认存在复用。
- **Agent 接口与 sandbox：** 能画出模型动作、工具观察、预算、停止和独立评分的调用关系；说明容器挂载、网络、进程权限及隐藏测试边界，解释为什么不能让生成的 shell 命令直接在宿主运行。
- **配对评测与失败分类：** 能回答为何同题同模型同预算比较、为何多个 seed 不等于多个独立任务、环境失败为何不能记作模型奖励 0；能从轨迹解释一项成功和一项失败，而非只展示平均分。
- **RL 的可核验奖励与新鲜轨迹：** 能从真实测试输出核对 reward，解释 action-token mask、log-prob、advantage 和梯度。对本项目的 on-policy 更新，要理解为何按当前策略重新采样 fresh rollouts，不能把旧策略或旧评分器产生的轨迹直接当作当前策略数据；能说明同组奖励相同时为何没有相对学习信号。

数学基础按这些问题补齐条件概率、对数似然、期望与方差、梯度、交叉熵和策略梯度；系统基础补齐进程、I/O、超时以及吞吐和延迟取舍。不必在开始前学完全部课程，但不能跳过自己实现所依赖的概念。

**项目由助手协作完成，不等于学生已经掌握项目。** 每周至少做一次脱离助手的检查：从一条轨迹定位错误、自己修改一个模块并解释测试、复算一次 token 或 advantage、讲清一个失败为什么不能支持原假设。面试时能够说明自己承担了哪些设计、实现和实验，不能把不理解的生成代码当作个人算法能力。

## 本轮服务器实施边界

本轮只进入可行性与测量阶段：在云端 RTX 4090 24GB 上配置 **7B 模型的 BF16 推理**，以已有开发任务 `astropy__astropy-12907` 诊断真实 Agent、补丁导出和官方 grader 链路。BF16 权重本身只是显存占用的一部分，KV cache 和运行开销仍须实际测量，不能仅凭参数量保证任意上下文都能运行。

本轮选用已知的 7B 旧基线，是为固定模型与工具协议、控制诊断变量，并不代表它是 2026 年最强或最有代表性的模型。后续正式实验仍需评估模型是否有足够任务能力，并说明与更强模型或官方 Agent 的差距；不能以一道开发题的结果作为求职项目的主要成绩。

该任务已经属于开发集合；即使成功，也只证明这个模型和环境下的单题链路，不形成上下文策略收益、总体 SWE-bench 分数或 RL 提升结论。若模型、镜像、依赖或评分不能在时间内完成，应保存明确的失败阶段与日志，不用 scripted 结果代替。

上述云端实施描述属于此前 v3 阶段；其后的 v4 实例也已经归还，不存在本文所声称的当前租约。后续多题、多策略、多次采样或后训练，需要根据已测得的单题耗时、镜像存储和模型开销，另行估算云卡/API费用并取得授权；历史两小时、总额不超过 10 元的授权不能自动扩展成六周预算。v5 的代码与 CPU 工作不产生云卡或模型调用费用。

本轮验收的是“能否得到可信的真实任务实验”，长期验收才是“是否形成面试中可以深入讨论的、可复现的技术结论”。结果可以支持改进，也可以支持采用更简单的基线；两者都必须以实际证据为依据。
