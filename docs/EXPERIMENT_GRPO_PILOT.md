# GRPO 试跑：单卡、harness rollout 上的 LoRA GRPO（工程验证）

本协议在运行前冻结，写于 2026-11-06，第一轮 RFT 的学生评测尚未完成。运行后只追加结果，不修改下面的判据。

## 问题

单卡 GRPO 循环能否端到端跑通：rollout、分组和 advantage、更新、把新 adapter 热加载回 vLLM。每个阶段花多少时间，数值是否健康？

这是工程验证。只跑 3 步，不对能力提升下任何结论。

## 设置

- **初始策略**：第一轮 RFT 得到的学生模型（合并后的 Qwen2.5-Coder-1.5B）。
  - 第一轮里基线学生在训练集上是 0/192，组内没有方差，GRPO 拿不到梯度，所以不从基线学生出发。
- **任务**：第一轮教师在训练集上至少解出过一次的题（33 题）。每步 8 题，每题采样 8 次（G = 8），共 64 次尝试。
- **rollout**：
  - 与评测相同的 `run_task` harness，以 `nobody` 用户执行，temperature 为 1.0。
  - 开启 `api_logprobs`：记录采样到的 token、行为策略（vLLM）的 logprob，以及 vLLM 实际使用的 prompt token 摘要。
- **训练**：
  - LoRA r = 32，α = 64，学习率 2e-5。
  - 每批只做 1 次更新，loss 按 token 级聚合，TIS 上限为 2，clip 为 0.2/0.28。只更新 1 次时 ratio 恒等于 1，clip 实际不起作用。
- **同卡共置**：vLLM 占 45% 显存，开启运行时 LoRA 加载。每一步保存新的 adapter 并热加载，不重启服务。
- **评分语义**：verifier 超时记为失败（PR #11）。第一轮仍按旧语义记为"未评分"。

## 每步记录

- 耗时：rollout、训练、同步（保存并热加载 adapter）。
- 通过率、保留的组数、被过滤掉的组数（全对或全错）。
- 训练用到的 turn 数、completion token 数，以及 prompt 摘要不一致的 turn 数。
- TIS 权重均值、被截断的比例、采样端与训练端 logprob 的平均绝对差。
- 熵、梯度范数、整个过程的峰值显存（每秒采样一次）。

## 验收（工程）

1. 每个保留下来的 turn，训练端用自己的模板重新渲染出的 prompt，与 vLLM 实际采样时的 prompt 在 token 层面完全一致，即 `prompt_mismatch` = 0。
2. 每一步的新 adapter 都能热加载，并且被下一步的 rollout 使用，服务不重启。
3. 不出现显存不足。
4. 记录采样端与训练端 logprob 的平均绝对差。预期远小于 0.1 nat。如果更大，说明两端数值不一致，要先排查，再做正式的 RL。

## 预算

约 1 小时 GPU。估算依据：每步 rollout 3 到 5 分钟，训练 5 到 15 分钟。

## 已知局限

- 3 步说明不了学习效果，而且每批只更新 1 次。
- 训练是逐 turn 进行的，同一次尝试里各 turn 共享的 prompt 前缀会被重复计算。这是目前最大的计算开销，本次测量会直接给出它的代价。

## 追加：试跑结果（2026-11-06 14:00–14:19 UTC）

**第 0 步完整跑通，验收项 1、3、4 通过。**
- 8 题 × 8 次采样，rollout 用时 128 秒。通过率 20.3%（13/64），8 组里有 5 组成败混合被保留，3 组全错被过滤。
- **prompt 一致性**：训练端重新渲染了 738 个 turn，与 vLLM 实际采样的 prompt 在 token 层面全部一致（`prompt_mismatch` = 0）。
- **数值**：
  - 采样端与训练端 logprob 的平均绝对差为 0.00175 nat，远低于预设的 0.1；
  - TIS 权重均值 0.99999，没有被截断的；
  - 只更新 1 次时 ratio 恒等于 1，与预期一致；
  - 熵 0.072，梯度范数 0.045。
- **显存**：vLLM 加上训练进程，约 33.6 GiB，没有显存不足。
- **adapter 热加载**：保存 v1 并热加载、卸载 v0，用时 0.8 秒，服务没有重启。
- **成本**：训练 738 个 turn 用时 849 秒（29,062 个 completion token），是 rollout 用时的 6.6 倍。逐 turn 重新编码 prompt 是目前的主要开销。

**第 1 步崩溃，验收项 2 只完成了一半。**
- 原因：PR #10 把 minibatch 的打乱顺序存进了名为 `order` 的变量，覆盖了跨步的任务调度。第 0 步结束后，调度表变成了 738 个 turn 的一个排列，第 1 步取任务时下标越界（`IndexError`）。
- 脚本的退出处理停掉了自己的 vLLM，GPU 被释放。
- v1 已经热加载成功，但"被下一步的 rollout 使用"这一项没有验证到。

**处理。**
- 打乱 turn 的变量单独命名（PR #15）。
- 多步运行和"新 adapter 被下一步 rollout 使用"，由第二轮 GRPO 的前几步验证。第二轮另有冻结协议。
- 第 0 步的数据和 v1 adapter 都保留在服务器上。
